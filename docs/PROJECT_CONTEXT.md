# PROJECT_CONTEXT.md

This file holds the detailed, session-by-session build history for the AI Employee Vault: every "Completed Phase" entry (what was built, why, and how it was verified) and the incident log. It's split out of `../CLAUDE.md` purely for size — `CLAUDE.md` was exceeding practical context-loading limits (150k+ characters) once this history accumulated.

**`CLAUDE.md` is the source of truth for current, active rules** (architecture, business rules, helper scripts, known constraints). This file is historical/reference material: read it when you need the *why* behind something already described in `CLAUDE.md`, or need details of a past verification pass. Do not treat anything here as a live instruction unless `CLAUDE.md` also says so.

- **### Pre-deployment code review — critical Odoo autonomy gate + discount-ceiling drift + unaudited rules endpoint fixed (2026-08-11):** Business owner requested a code review specifically to decide go/no-go on deploying this vault for real and handing it to a paying client. A `code-reviewer` subagent reviewed every live-action/safety-critical path (Gmail send, social posting, Odoo invoicing/payments, the Web GUI's approval/confirm-live flow, auth/CSRF, zone-gating). Verdict: conditional no-go until one CRITICAL finding was fixed; two HIGH findings also fixed same session before sign-off.
  - **CRITICAL, fixed — `create_odoo_invoice()` had no `EXECUTION_ZONE` gate at all**, unlike its siblings `cancel_odoo_invoice()`/`record_payment()` (both already correctly gated). Now that real `ODOO_API_KEY`/`ODOO_URL` are live on both machines (per the 2026-08-10 fix), the always-running Cloud `agent-runner.service` could have silently created real invoices in the client's live Odoo database for any qualifying deal trigger, with **zero human review** — a direct breach of the Company Handbook's "any financial transaction routes to `Pending_Approval/`" rule. The code comment calling this "Cloud Agent has draft-create only" design was written when Odoo credentials were known-broken (401 error); it stopped being safe the moment those credentials went live. **Fix**: added the same `is_cloud_execution()` gate `cancel_odoo_invoice`/`record_payment` already use — `EXECUTION_ZONE=cloud` (default) now returns a sandbox mock invoice number and makes no live Odoo call; only `EXECUTION_ZONE=local` can create a real invoice record. `cancel_odoo_invoice`'s docstring (which referenced the old "draft-create only" design) was updated to match. Verified via static read + `py_compile`; a runtime cloud-zone test was intentionally not run this session (user was mid-edit on the real `.env` in their IDE at the time).
  - **HIGH, fixed — deal-pipeline discount ceiling hardcoded 15%, contradicting the documented 20% KB rule.** `mcp_servers/agent_runner.py`'s "deal pipeline" branch (the generic non-email/non-WhatsApp trigger path) checked `discount_rate > 15.0` and escalated above it — but `Knowledge_Base/knowledge_base.md` and both `triage_email`/`triage_whatsapp` in `vault_server.py` use 20% as the autonomous-authorization ceiling. This meant the *same* discount request got a different auto-approve/escalate outcome depending on which channel it arrived through, and the pipeline fetched `search_kb("discount")` guidance but never actually used it — the ceiling was a stale hardcoded number, not KB-derived, contradicting this vault's own "never hardcode rules, query the KB" principle. **Fix**: replaced the magic number with a named `DISCOUNT_CEILING = 20.0` constant matching the KB, with a comment cross-referencing `knowledge_base.md` §3 and the other two triage paths so the three don't drift apart again unnoticed.
  - **HIGH, fixed — `POST /rules/save` (the Web GUI page that edits the autonomous discount ceiling itself) had weaker protection than a routine social post.** It was gated only by session login + CSRF — no typed-confirmation requirement (unlike every live-send/post/pay action, which requires typing `SEND`/`POST`/`RECORD`/etc. per the Phase 3 confirm-live pattern) and, notably, **no audit-log entry at all**, despite this single field controlling every future deal's auto-approve/escalate decision. **Fix**: `web_gui/templates/rules.html` gained a required "type `CONFIRM` to save" field (amber-highlighted, same visual convention as a live-action warning); `web_gui/app.py`'s `rules_save()` route now rejects the submission unless `confirm_text.strip() == "CONFIRM"`, and on success calls `vault_ops.append_audit_log("BUSINESS_RULE_CHANGE", "Business", ...)` recording the old→new ceiling value and the other three fields changed — the same `Audit_Logs/audit_log.json` trail every other consequential action in this vault already gets.
  - **MEDIUM, noted but not fixed this pass (lower priority, not blocking)**: `record_payment()` has no idempotency guard beyond checking for a fully `'paid'` invoice state — a manual retry after a partial failure could create a second `account.payment` record with no dedup check against an existing transaction reference. Also, `_looks_like_placeholder()`-style live/sandbox credential detection in `social_server.py` uses slightly different marker substrings per platform (Twitter/Meta/LinkedIn) rather than one shared helper — low risk (fails safe toward sandbox) but a maintenance smell given this vault's own history of credential-field mixups (see the 2026-08-10 LinkedIn/Twitter entries).
  - **Confirmed already solid, not touched**: the live-action layer's fail-safe `EXECUTION_ZONE` defaults, redundant zone-checks at multiple layers (`execute_live_action()`'s own Phase 9 defensive re-check), typed-confirmation-word gates, non-interactive-stdin refusal on `send_approved_emails.py`/`process_approved_payments.py`, safe failure semantics (a failed send/post/pay leaves the draft untouched rather than double-firing), Odoo's never-delete-only-transition-state invoice handling, secrets exclusion from git/Syncthing, and `Dashboard.md`'s single-writer rule.
  - **Deployment follow-up still needed (not done this session)**: these fixes exist in the working tree on the machine this session ran on — they must be pushed/pulled to wherever `agent-runner.service` and the Web GUI actually run in production (per Current Architecture State, the Cloud VM at `/home/ubuntu/ai-employee-hackathon`) and both services restarted before they take effect live.
